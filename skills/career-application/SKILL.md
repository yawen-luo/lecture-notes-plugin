# Career Application

Produce credible, concise, highly role-specific application materials that show **what the applicant's evidence proves about suitability for the role**, not a list of tasks, fashionable technologies, or unsupported praise. Combine three formerly separate workflows: Resume/CV Tailoring, Cover Letter Writing, and Independent Application Review & Scoring.

## 1. Select the task mode before working

- **Write / tailor**: create a new resume, academic CV, cover letter, or requested application statement; or adapt an existing draft to an identified opportunity.
- **Review / score**: independently audit a completed draft against eligibility, the actual brief/JD, verified facts, and the original rubric. Do not write a replacement unless requested.
- **Format / export**: produce the specifically requested editable file or layout (e.g., LaTeX); keep layout decisions separate from truthful content.
- **End-to-end**: match requirements to evidence, draft, run an independent review pass, revise, and report unresolved facts.

Apply only the requested mode(s). For a small rewrite, return the replacement text rather than a compulsory full report. Do not treat the skill as an application submission or email-sending authorization.

## 2. Read only task-relevant reference files

- For **all** tasks, read [evidence-and-opportunity.md](references/evidence-and-opportunity.md).
- For **cover letters**, read [cover-letter.md](references/cover-letter.md).
- For **resumes or academic CVs**, read [resume-cv.md](references/resume-cv.md).
- For **independent review, scoring, or the final audit of end-to-end work**, read [review-scoring.md](references/review-scoring.md).
- For **LaTeX, PDF, layout, headers, or template requests**, read [format-and-templates.md](references/format-and-templates.md); load the appropriate asset only when needed.

References are authoritative workflow details, not permission to invent source facts. When connected personal Notion resources are available, use the user's current Evidence Bank, rubrics, and template sources; this public skill contains no personal record.

## 3. Apply source and instruction precedence

1. User's current explicit intent and constraints, within mandatory external rules.
2. Official, current target opportunity or program requirements, eligibility, prescribed template, and user-supplied original scoring rubric.
3. Current **verified** applicant source documents, original project records, transcript, and applicant-confirmed facts.
4. The user's approved reusable preferences and their private Evidence Bank after verification.
5. Earlier drafts, generic examples, or external template placeholders — never evidence of personal history.

When two sources conflict, label the conflict and verify instead of silently selecting the stronger-sounding claim. Do not treat a previously generated AI draft, example letter, syllabus, project plan, or unreleased prototype as proof of an accomplished result.

## 4. Follow the common workflow

1. **Establish the target.** Identify exact organization, role/program, Req ID, application channel, official requirements, hard eligibility criteria, deadline, location/work arrangement, requested materials, and intended reader. If the task is to evaluate a live opportunity, verify current page, open status, and valid application entry; historical JD notes do not prove a posting is still open. Do not assert unverified status.
2. **Extract the decision criteria.** Identify the 3–5 most important capabilities/responsibilities and their required or preferred status. For academic programs, use the stated prompt and evaluation criteria rather than inventing a JD.
3. **Verify the applicant evidence.** For each claim separate personal work, team work, in-progress work, planned work, and results independently verified. Check names, dates, degree, graduation year, GPA, language test validity, project state, publications, and any numbers before inclusion.
4. **Map evidence to reader value.** Use: Requirement → specific verified example → applicant's own action → outcome or inspectable deliverable → why that demonstrates relevant ability. Mark unrelated matches as irrelevant; a tool name alone does not prove skill.
5. **Choose a narrative.** Prioritize the highest-relevance examples, accurate action verbs, and clear transferability. Demonstrate impact, relevance, and personal contribution; never list responsibilities without making their significance clear.
6. **Draft the requested document.** Apply the relevant format-specific guide. Use direct professional English, appropriately scoped claims, audience-appropriate explanations, and the shortest sufficient response.
7. **Run a genuine independent quality pass** when the user asks for review or an end-to-end draft. Check hard failures first, then mapping, evidence, six quality dimensions, consistency, and the original rubric if provided. Do not inflate scores on your own writing.
8. **Revise surgically and recheck against the same standard.** Surface unresolved verification items outside the final submission text.

## 5. Non-negotiable truth and ethics safeguards

- Never invent employment, internship, lab affiliation, project deployment, authorship, publications, acceptances, awards, leadership titles, metrics, user studies, revenue, performance improvements, independent ownership, or credentials.
- Do not promote hackathon participation to paid employment; planned experiments to completed studies; submissions to publications; internal prototypes to shipped commercial products; team output to individual achievement.
- Quantify only traceable numbers. When no metrics exist, describe a concrete deliverable, scope, evaluation, or validated output without inventing percentages.
- Do not silently invent job sources, organization addresses, named hiring managers, requisition IDs, or work eligibility. If essential inputs are absent, ask the minimum necessary question; otherwise proceed conservatively with explicit gaps.
- Keep raw private applicant data, credentials, transcripts, reference letters, and project files out of public Git repositories and generated public examples.
- Include AI-use disclosure only if explicitly required by the school, course, recruiter, journal, or submission platform; accurately reflect actual model/use when required. Never insert an automatic AI disclosure paragraph into a recruiter cover letter.
- Use academic-writing conventions only for academic text; recruiter-facing letters can naturally use "I" and the active voice.

## 6. Deliverables and editing discipline

- **Cover letter**: a brief writing strategy (at most five short points), submission-ready letter, and rubric/reality check when review or end-to-end mode was requested; see cover-letter reference.
- **Resume/CV**: short positioning summary, the requested full draft or directly replaceable bullets, meaningful change notes, and unresolved facts; see resume reference.
- **Review only**: verdict (pass/fail/unverified), evidence-grounded rubric findings, and up to 3–5 prioritized actionable fixes; no mandatory rewrite.
- **Formatting**: editable source when requested, file/layout validation where tools permit, and no claims of compile success unless a compilation actually ran.
- **Minimal requests**: if asked only for a short paragraph, a bullet, a subject line, or an edit, return only that.

Do not automatically create or overwrite a Notion page, change the applicant's canonical Evidence Bank, send a message, submit an application, or produce PDF/DOCX/TeX files unless asked. Before changing any connected document, preserve existing content, use targeted edits, and verify the result.

## 7. Final gate

Before delivery, ask internally: Is the target correct and eligible? Are the most important requirements supported by specific applicant actions? Can every material fact be traced? Does the document distinguish personal contribution from team achievements? Are word/page limits and naming accurate? Is the style right for the actual reader? Have unsupported facts been kept out of the deliverable? If any answer is uncertain, mark it for verification rather than inventing certainty.
